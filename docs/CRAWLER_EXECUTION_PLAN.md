# 爬虫与索引流水线优化执行计划

日期：2026-11-20  
状态：P0 的观测与基线采样已完成，分支 feat/crawler-p0-observability；P1 的写入一致性、专用数据库线程和启停闭环已实施，验证记录见 [P1 报告](./CRAWLER_P1_REPORT.md)；P2 的批量查重、写入确认和限速通知已完成，验证与测量见 [P2 报告](./CRAWLER_P2_REPORT.md)；P3～P5 尚未实施。三轮正式网络采样已执行，吞吐结论受少量输入和请求超时限制，详见 [P0 报告](./CRAWLER_P0_REPORT.md) 与 [工具说明](../benchmarks/crawler/README.md)。未据此声称高负载容量或多线程收益已获验证。

## 1. 目标与现状

目标是在保持索引、文件详情、统计和搜索行为正确的前提下，提高成功收录吞吐量，减少主线程阻塞，并限制网络故障或数据库积压时的资源占用。

当前已核对的实现：

| 环节 | 当前行为 | 代码位置 |
| --- | --- | --- |
| 网络通信 | librats 后台处理 DHT 和 BitTorrent 通信 | [bittorrent.cpp](../src/librats/src/librats/subsystems/bittorrent.cpp) |
| 发现与查重 | 公告入口限量，Qt 主线程状态去重后提交专用线程批量查重 | [crawler.cpp](../src/net/crawler.cpp)、[application.cpp](../src/app/application.cpp) |
| 元数据获取 | 异步并发，上限固定为 10；底层每次请求创建一个等待线程 | [crawler.h](../src/net/crawler.h)、[bittorrent.cpp](../src/librats/src/librats/subsystems/bittorrent.cpp) |
| 爬虫入库 | 元数据回到主线程后，通过有界队列按条数/时限提交专用数据库线程批量写入 | [indexing_service.cpp](../src/services/indexing_service.cpp) |
| 批处理 | 导入默认不发送逐条通知；爬虫批次确认新增后限速通知 | [indexing_service.h](../src/services/indexing_service.h) |
| 数据库连接 | 按调用线程创建并清理连接；所有仓库写入共用读改写协调器 | [manticore.cpp](../src/data/manticore.cpp) |
| 其他写入 | 远程数据、导入、投票、tracker、文件补齐等也会修改索引 | [services/](../src/services/)、[peer_api.cpp](../src/peer/peer_api.cpp) |

上一轮文件显示修复是本计划的回归基线：搜索片段不能作为完整文件列表；已知文件数量不能代替完整性判断；完整列表不能被部分列表覆盖；详情补取结果不能覆盖新选择。

非目标：本轮不改变 DHT 协议，不引入多个爬虫实例，不更换数据库，不默认启用多个并行写入线程，也不承诺未经测量的性能倍数。

## 2. 目标结构与必须保持的约束

```text
librats 网络线程
  → 有界公告入口（在产生大量 Qt 排队事件之前合并/限量）
  → 发现队列 → 后台批量查重 → 元数据候选队列
  → 有界异步元数据获取
  → 待入库队列（条数 + 估算字节数限制）
  → 专用数据库工作线程（分类、过滤、批量合并与写入）
  → 排队完成通知 → 主线程更新界面与调度 tracker
```

必须保持：

1. 工作线程使用自己的数据库连接；连接在所属线程内关闭和移除。
2. QObject 的事件、定时器和界面操作遵循线程归属；不能把现有服务指针交给线程后直接任意调用。
3. 相同规范化 hash 的查重、合并、写入与统计具有一致的串行语义；不同 hash 的 63 位 ID 碰撞仍必须核对完整 hash。
4. 数据库仍是事实来源。缓存只降低重复工作，查询失败不得被当成“不存在”。
5. 队列容量覆盖已排队、在途结果和重试数据；不能用无界 Qt 事件队列绕过容量限制。
6. 每个任务携带运行代次、任务 ID、配置版本；旧代次回调不能改变当前代次的名额和状态。
7. 爬虫开关、过滤设置、暂停退出行为、tracker 通知和已有文件详情修复保持兼容。
8. 双索引写入不是事务；必须识别部分成功，禁止把整个部分成功批次当成全新批次盲目重放并累加统计。

## 5. P1：写入一致性与专用数据库工作线程

### 实施步骤

- [x] **P1-01：建立写入矩阵。** 列出爬虫、P2P、单条/批量导入、投票、tracker、文件补齐、删除和迁移的执行线程、读改写步骤、统计与通知。特别检查“读取旧对象后 REPLACE”是否覆盖并发局部更新。
- [x] **P1-02：先建立一致性边界。** 优先采用统一写命令协调入口；异步爬虫走排队任务，尚需同步结果的调用使用受控同步入口。将读取待合并记录和提交作为一个协调操作，不能只锁最后一条 SQL。必要的过渡锁位于非 QObject 的共享协调对象，锁内禁止等待主线程或发送可重入的外部通知。确定方案并增加并发回归后，才切换爬虫写入。
- [x] **P1-03：新增工作对象。** 已由 crawler_pipeline 控制器与其专用线程执行器分别承担调度/容量管理和数据库任务。通过 queued connection 传值；工作线程内创建本地过滤、入库服务并使用所属线程的连接。未整体移动 Application 已共享的仓储/服务；共享仓库同步方法经写协调器保护。
- [x] **P1-04：迁移爬虫数据库操作。** 将已知 hash 检查与入库发送到后台；删除主线程同步 knownHashFilter 数据库路径。先保持单条语义，任务提交接口从本阶段起就有容量限制和拒绝结果。
- [x] **P1-05：完成启停闭环。** 定义 Starting、Running、Draining、Stopped 状态；增加运行代次及在途账本。过滤配置在主线程生成不可变快照，由工作线程在任务/批次边界切换并回报版本。配置重载、连接异常和应用退出不能依赖主线程阻塞期间再处理其事件才能完成。

### 生命周期细节

暂停爬虫时先停止新任务接纳，撤销未启动候选，按既定策略处理已经获取成功的待入库任务；普通停用与应用退出采用明确、可测试的 drain 策略。重新启动生成新代次，不能直接把活动计数清零后接受旧回调。

应用退出顺序：关闭新的外部写入入口 → 停止爬虫接纳 → 停止产生新 tracker/复制任务 → 协调导入等其他写入生产者退出 → 等待在途获取结束或取消 → 刷新待入库结果 → 在所属线程释放 SQL 连接 → 退出工作线程 → 释放网络与数据库依赖。实际顺序须结合 [Application::stop](../src/app/application.cpp) 和网络取消能力确认；禁止强杀线程。

若达到排空期限，记录未完成条数与原因。若队列未持久化，就明确报告其不会跨进程恢复，不能宣称零丢失。

### 验证与验收

增加线程归属断言/测试；覆盖同 hash 并发入库、入库与删除、文件补齐与投票合并、批量导入与爬虫并发。SQL 连接数量在重复启停后应回落；工作线程退出不能留下命名连接。

**验收：** 主线程不再同步执行爬虫查重/入库；并发写入不重复统计、不丢局部更新；正常及异常退出无死锁、悬空回调或数据库先关闭问题。首次性能判断只报告结果，不以线程迁移本身作为提速证据。

P1 的写入矩阵、容量默认值、停止取消策略、连接清理与验证证据详见 [P1 实施报告](./CRAWLER_P1_REPORT.md)。本次采用仓库内非 QObject 写协调器作为过渡；工作线程构造本地过滤与入库服务，通过经审核的同步仓库方法访问按线程创建的 SQL 连接。

## 6. P2：后台批量查重与批量入库

### 实施步骤

- [x] **P2-01：规范化并合并候选。** hash 统一小写，pending/inflight/retrying 状态显式去重；同 hash 的额外 peer 地址保留有限个备用项。缓存容量和有效期有上限；失败 hash 不永久屏蔽。
- [x] **P2-02：批量查重。** 初始建议达到 100 条或最老任务等待 100 毫秒即提交，稀疏流量也能及时推进。使用 ID 批量查询并验证完整 hash。结果明确区分已存在、缺失、碰撞和查询失败；失败批次不可全部当作新 hash 启动抓取。对摘要存在但详情不全的候选制定修复路径，不能永久跳过。
- [x] **P2-03：批量写入。** 同样以条数/等待时间触发；分类和过滤在后台执行。复用 [insertBatch](../src/services/indexing_service.cpp)，按条数和实际 SQL 大小拆批，遵循现有数据包保护。大文件列表参与字节预算，单个超限任务明确拒绝或单独处理。
- [x] **P2-04：准确报告提交结果。** 扩展批量结果结构，携带新增/合并/过滤/碰撞/失败的 hash 与原因，区分文件索引和摘要索引阶段。逐个 SQL 子批次确认成功，并在失败后重查已提交 ID，避免在 REPLACE 重试时重复增加统计。多语句部分成功纳入测试，不能只返回一个模糊的 inserted 数值。
- [x] **P2-05：保持完成通知。** 只有确认新增的种子发送批量完成事件。主线程通过限速队列分发 tracker 查询和 UI 更新；合并/重试不得重复触发“新种子”动作。已有导入接口继续默认不触发海量 tracker 请求，使用显式来源或选项区分爬虫与导入。

### 优化与正确性细节

已在批量查询与写入边界区分查询失败、缺失、碰撞、详情不全及逐项提交状态。相关落点为 [database.cpp](../src/data/database.cpp)、[torrent_repository.cpp](../src/data/torrent_repository.cpp)、[indexing_service.h](../src/services/indexing_service.h)。

统计仅按确认发生的新增/变更计算；部分提交、重新导入、大小写 hash、同批重复和 ID 碰撞必须分别验证。保留完整文件列表优先的合并规则；批次大小必须在 Manticore 返回行数和 max_matches 限制内，显式设置 LIMIT。

**验收：** 固定数据下 SQL 往返次数下降，计数/文件列表与单条基线一致；低流量提交等待符合批次时限；拆批中途失败可恢复且无重复统计；tracker 通知准确。报告吞吐量和 p95 延迟，不能只展示单批最快耗时。

## 7. P3：完整背压与有限重试

### 实施步骤

- [x] **P3-01：统一容量账本。** 初始试验值：发现入口最多 5,000 条；待入库最多 1,000 条且估算内存最多 64 MiB。条数或字节数任一达到上限即限制接纳。参数最终依据实测调整，硬上限必须校验。
- [x] **P3-02：实现高低水位。** 初始高水位 80%、低水位 50%；待入库高水位时暂停发起新元数据请求，低水位后恢复。DHT 候选入口满时丢弃新候选并记原因；已完成元数据优先处理。必要时减少 spider walk 调度，网络维护消息仍需处理。
- [x] **P3-03：为在途结果预留容量。** 调度请求前预留结果名额和预算；完成后转换为实际占用并释放预留。规定单个结果上限及超限行为，防止大量在途请求同时完成突破内存预算。Qt 调用只发送有界 mailbox 的唤醒信号，避免每条公告都排一个无限增长的闭包。
- [x] **P3-04：按错误分类重试。** 网络超时可切换有限备用 peer；数据库暂时不可用可退避；校验失败/过滤拒绝/ID 碰撞不重试。初始重试最多 3 次，指数退避带抖动且总时长封顶；重试队列与正常队列共享容量，取消或旧代次任务不再重试。

### 验证与验收

使用可注入的数据库延迟、失败和元数据结果，覆盖突发公告、持续超时、数据库离线后恢复、大元数据同时返回及重试耗尽。检查账本始终满足上限，暂停/恢复不振荡、不丢唤醒，恢复后旧任务不会饿死新任务，反之亦然。

**验收：** 可控过载下队列有界、内存不持续增长；恢复后自动继续；记录接纳、完成、拒绝、取消、剩余任务可对账。估算字节数与实际 RSS 分开报告，不能把估算值称为进程内存硬上限。

P3 的容量参数、重试分类、停止时保留预留的规则与测试证据见 [P3 实施报告](./CRAWLER_P3_REPORT.md)。

## 9. P5：异常恢复、长时运行与发布收敛

### 实施步骤

- [x] **P5-01：确定性测试。** 使用可控时钟和假元数据接口，验证状态转移、批次触发、队列预算、运行代次隔离、重试和通知。避免靠长 sleep 触发竞态；对重复完成、乱序完成、同步失败回调都要覆盖。
- [x] **P5-02：真实数据库集成。** 扩展 [test_manticore_queries.cpp](../tests/test_manticore_queries.cpp)，覆盖并发来源、大小写 hash、碰撞、文件补齐、投票合并、批次拆分中途失败及重试。故障测试使用临时目录和独立实例，不能操作用户库。
- [x] **P5-03：启停与长时验证。** 可控环境建议连续运行 2 小时、至少 100 次启停，确认线程、连接和队列不泄漏；真实网络建议 2 小时作为首轮持续运行窗口。覆盖导入并行、数据库断连、配置更新、退出时在途请求、停止后立即重启及晚到回调。
- [x] **P5-04：报告和默认值收敛。** 保存 P0 与最终版本的可比较数据、复现命令、错误样本、已知限制。更新用户手册和设置说明，说明队列丢弃、重试与退出时未完成数据的语义。

P5 的故障回归、两次独立两小时 / 各 100 次启停、资源趋势及默认值结论见 [P5 实施报告](./CRAWLER_P5_REPORT.md)。全量 CTest 31/31 通过；公网样本仅 4 次尝试、1 条新增，不据此宣称整体吞吐提升；内存小幅增长如实保留，不宣称所有泄漏均被排除。

### 最终验收矩阵

| 场景 | 必须满足 |
| --- | --- |
| 同 hash 重复/并发发现 | 一份记录，新增与统计不重复 |
| 文件列表缺失/截断 | 完整输入可修复，部分输入不会覆盖完整列表 |
| 导入、投票、tracker 与爬虫并行 | 不覆盖彼此字段，完整 hash 校验仍有效 |
| 数据库查询失败 | 不被误认为所有候选都未入库 |
| 批次部分提交 | 能识别已提交项，重试不重复统计/通知 |
| 元数据失败/超时 | 名额只释放一次，重试和备用 peer 有上限 |
| 高水位和突发完成 | 按预算背压，恢复后继续推进 |
| 停止/重启与旧回调 | 新代次计数不受旧回调影响 |
| 退出与连接释放 | 无死锁，数据库最后关闭，无遗留工作线程 |
| 搜索和底部文件窗口 | 上一轮文件显示回归持续通过 |

## 10. 执行命令、回退和完成定义

Windows 使用项目已提供的本地 Qt/CMake 工具链。实施时先核对实际构建目录和环境，命令示例：

```powershell
$env:PATH = "$PWD/.tools/Qt/Tools/mingw1310_64/bin;$PWD/.tools/Qt/6.10.1/mingw_64/bin;" + $env:PATH
& .tools/Qt/Tools/CMake_64/bin/cmake.exe --build build-windows-x64 --target rats-search test_manticore_queries test_download_ui -j 4
& .tools/Qt/Tools/CMake_64/bin/ctest.exe --test-dir build-windows-x64 -R '^(test_manticore_queries|test_download_ui)$' --output-on-failure
git diff --check
```

新增流水线测试目标后加入阶段构建/测试命令。P1 起同步运行受影响的配置、导入导出、投票与生命周期测试；最终执行完整项目测试。测量配置、输入数据生成方式和原始结果保留在 benchmarks 下的专用目录，报告链接到实际输出。

回退以阶段提交为边界，不回退上一轮文件显示修复。初期可提供内部流水线开关，但切换前必须停止接纳并排空/取消当前任务，禁止旧新写入路径同时处理同一队列；数据库格式尽量保持不变，不通过删除用户数据回退。

完成定义：正确性和生命周期验收全部通过，主线程爬虫数据库调用已移除，资源上限与恢复策略经过验证，性能对比数据可复现；若某项未获性能收益，应如实保留结论并收敛默认值。代码编译成功或线程数增加不能单独作为计划完成依据。
