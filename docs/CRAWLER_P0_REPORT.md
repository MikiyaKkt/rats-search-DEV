# P0 实施与基线报告

日期：2026-11-20。分支：`feat/crawler-p0-observability`。

## 状态

P0-01～03 的指标口径、观测实现、日志开关及自动化测试已经落地。P0-04 已完成可控数据库三轮基线，以及三轮“预热 5 分钟 + 测量 15 分钟”真实网络采样。P0 的观测与基线任务完成；真实网络仅观察到两次失败请求，不能据此宣称已经验证高负载吞吐量或多线程收益。

本分支从 master 创建，保留了进入 P0 前尚未提交的文件显示修复和执行计划；没有自动提交。基线源码为 `fa5abc8` 加当前工作区，不能把 HEAD 单独视作测量版本。运行相关文件的 SHA-256 见 [源码清单](../benchmarks/crawler/results/p0-source-manifest.json)。

## 实现范围

- [指标收集器](../src/common/performance_metrics.h)：线程安全累计计数、当前值/峰值、每键最多 1024 个样本；计数、gauge、sample 各最多 128 个固定名称；快照输出 count/mean/max 和最近样本 p50/p95。
- [汇总器](../src/common/performance_reporter.cpp)：每 5 秒 JSON 摘要、停止时最终快照、每 200 毫秒主线程事件漂移探测、区间收录速率和元数据完成比例。
- [爬虫插桩](../src/net/crawler.cpp)：公告交付、近期重复、已知 hash 查重、候选队列、元数据请求、结果交付队列和耗时；不调整抓取并发或队列策略。
- [数据库插桩](../src/data/database.cpp)：SQL 成功/失败、同步耗时、主线程调用数/耗时、写 SQL 字节数和 INSERT/REPLACE 拆分行数。
- [入库插桩](../src/services/indexing_service.cpp)：全来源单条/批量结果、查重、分类、过滤、持久化耗时；[应用连接](../src/app/application.cpp) 另外统计仅爬虫来源的入库结果。
- 成功路径逐条日志改为 `rats.crawler.detail` 调试分类。`RATS_METRICS=0` 禁用观测；`RATS_VERBOSE_CRAWLER=1` 在应用启动时开启逐条调试日志。

重试、背压、专用写线程和爬虫批量入库没有在 P0 提前实现。指标含义、估算内存限制、已有去重/批量确认语义和运行步骤见 [工具说明](../benchmarks/crawler/README.md)。

## 可控数据库基线

原始数据：[p0-controlled.json](../benchmarks/crawler/results/p0-controlled.json)。环境为 Windows 11、Qt 6.10.1、本地 Release/MinGW 工具链，Manticore 17.5.1；数据库、日志和输入均为临时 fixture。每模式实例预热 12 条，三种模式顺序轮换，各测三次，共 36 个场景结果。

时间单位 ms，表内为三次中位数：

| 场景 | 输入 | 关闭指标 | 开启指标 | 开启指标与逐条日志 | 开启指标时查询/写语句数 |
| --- | --- | ---: | ---: | ---: | --- |
| 新记录逐条入库 | 300 条，每条 4 文件 | 274.983 | 252.170 | 254.297 | 300 / 600 |
| 已有记录重复入库 | 300 条，每条 4 文件 | 176.397 | 176.361 | 179.910 | 600 / 0 |
| 大文件列表逐条入库 | 60 条，每条 256 文件 | 95.215 | 95.111 | 99.336 | 60 / 120 |
| 既有接口批量入库 | 300 条，每批 100 条 | 18.395 | 17.938 | 18.302 | 3 / 6 |

指标开启模式的三次范围分别为 246.678～256.650、175.039～179.428、94.689～99.355、17.597～17.941 ms。对照模式的范围分别为 252.417～283.327、174.472～178.197、93.073～98.227、18.322～20.466 ms。

本次指标开启相对关闭的中位数差约为 -8.30%、-0.02%、-0.11%、-2.48%；这些短场景受缓存/调度等波动影响，**负差值不代表指标会加速，不能据此宣称观测无成本**。verbose 相对指标开启的中位数差为 +0.84%、+2.01%、+4.44%、+2.03%，每场景详细日志约 75,900、38,700、15,300、720 字节。日志使用 QFile 接收器，不能等同于生产日志全部开销。

可确认的结构性结果：

1. 逐条新记录的查询与双索引写入是同步逐条发生的，当前基线均在主线程。
2. 重复记录还会检查已有文件详情，因此 300 条输入产生 600 次查询，不能用重复场景估计新记录成本。
3. 既有批量接口可以显著减少 SQL 往返；这为 P2 提供参考，不能直接折算成 DHT 爬取提速，因为网络元数据获取未纳入受控基线。
4. 所有 36 个场景均校验新增/合并结果、仓储统计与真实数据库 COUNT，一并抽查首尾完整文件列表。

该基线不包括网络、tracker、内容类型推断、持续过载或强制落盘延迟，也未测量数据库进程 CPU/RSS。程序关闭指标模式仍保留插桩分支，不是原始未插桩二进制。复现与汇总：

```powershell
& ./build-windows-x64/tests/crawler_benchmark.exe --output benchmarks/crawler/results/p0-controlled.json
& ./benchmarks/crawler/summarize.ps1 -InputJson benchmarks/crawler/results/p0-controlled.json
```

## 实时探针中的发现

沙箱内首次 20 秒探针 DHT 引导节点为零，并出现网络接口相关错误；沙箱外 20 秒探针能够完成引导，观察到路由表节点。两者均为冒烟测试，不能作为长期网络吞吐量基线。

沙箱外初次探针还发现：仅关闭 `p2pReplication` 并不能关闭 feed 同步及入站公告，20 秒内全来源索引新增报告为 551，而爬虫来源新增为零。这证明必须区分来源，不能把总索引增长当作 DHT 爬虫吞吐量。

已修改探针，在独立临时数据库内屏蔽会入库的 peer 响应/公告，并断开 PeerApi 的连接后同步入口；正式应用未作相应协议更改。

最终隔离探针运行 60 秒、无预热，结果见 [网络短测 JSON](../benchmarks/crawler/results/final-live/run-1-20261120-164750.json)：爬虫运行标志为 true，结束时 DHT 节点数为 151；窗口内没有公告、元数据尝试或入库活动。这只验证探针连接和观测链路，不用于估计有效吞吐量。

该短测记录 62 份进程资源样本（包含启动/停止），采样到的最大线程数 31、最大 RSS 69,181,440 字节，最后采样累计 CPU 6.71875 秒。事件漂移保留 299 个样本，p95 为 0.9342 ms、最大为 6.6487 ms。这些是先行短测数据，不是过载或长期稳定性结论；资源范围不含 searchd。原始资源 JSONL 按工具说明本地保留，不纳入版本附件。正式长测结果见下一节。

资源脚本每秒记录探针进程的 CPU、RSS、private bytes 和线程数，排除 searchd。正式对齐以结果内测量 UTC 为准，phase_estimate 只做参考。诊断日志可能包含种子名称或 peer 信息，未纳入报告附件。

三轮顺序运行，每轮使用独立临时数据库，预热 300 秒、测量 900 秒。实际正式测量总时长约 2700 秒，加上 900 秒预热，约 60 分钟。全部正常退出；测量期指标启用、爬虫运行，peer 入库隔离有效。

队列与 SQL 观测：

- 第 1 轮元数据队列的进程生命周期峰值为 1，在途请求峰值为 1；5 秒快照中的等待队列均为 0，说明快照可能错过很短的等待，不能说从未排队。第 2、3 轮没有元数据任务。
- 三轮都没有进入元数据成功交付/爬虫入库路径，没有持续的写入积压或实际写 SQL。
- 测量期主线程查询次数分别为 2、0、34。第 1 轮的两次对应爬虫已知 hash 检查；第 3 轮没有爬虫查重，其查询属于其他未细分路径。探针屏蔽 peer 入库，没有屏蔽所有只读 peer 请求，不能把所有 SQL 都算作爬虫工作量。
- 结束快照最近 1024 个事件漂移样本的 p95 分别为 2.379、0.828、0.658 ms；这不是整个 15 分钟的 p95，且没有高负载，不能外推界面在高吞吐时的响应能力。

网络条件与结论边界：

1. 三轮同机、同一构建、同参数顺序运行；探针关闭 tracker、复制、UPnP、打洞和中继，使用临时端口。它不等同于生产应用默认网络配置，没有验证公网入站可达性。
2. 5 秒快照中 DHT 节点范围分别为 129～192、83～192、72～178，说明持续发现了节点，但节点数不等于有效种子输入。
3. 全部探针生命周期（包含预热/退出）的 UDP 地址错误 10049 日志行数分别为 36、38、43。该统计不是测量期错误率；不能据此断言它导致了两次元数据超时。
4. 在本次固定条件下，实际限制首先表现为公告极少和已有请求超时；未观察到入库吞吐饱和。当前数据不支持“增加入库线程即可提高本次网络收录量”的结论。数据库批处理潜力仍由前面的可控基线支持。
5. 后续若要验证吞吐提升，应增加端口可达性/普通网络配置的对照，并使用足够的成功元数据输入；保持观测口径一致，不将未测效果写成已验证收益。

## 结论限制与下一阶段入口

- P0-04 已完成三轮 5+15 分钟网络采样，并保存环境、有效测量窗口、资源汇总及原始无内容指标；成功网络负载过少，高吞吐容量和优化收益仍未验证。
- 当前近期去重集合不具备严格 pending/inflight 状态，查询失败也可能沿用现有“无记录”返回语义；P0 暴露其错误计数，没有改变这些行为。
- 当前双索引与拆分批次没有完整事务确认模型，批量新增指标明确标记为 reported；P1/P2 必须解决跨来源一致性及部分成功重试。
- 暂无稳定的端到端观测开销结论；下一轮应扩大可控用例、增加重复次数并独立采集数据库资源，不能据此直接提高默认并发。
- 后续先推进计划中的写入矩阵、线程生命周期与一致性测试，再迁移数据库工作线程。
